01 — Descripción de la aplicación

1. Qué es

Conduit es una aplicación web de publicación de artículos (blog social tipo Medium) que implementa el contrato de API RealWorld: usuarios, artículos, etiquetas, comentarios, favoritos y seguimiento entre usuarios. Es el caso de estudio que la comunidad RealWorld usa para comparar implementaciones de stacks completos.

El proyecto del integrador reutiliza el backend de referencia (node-express-realworld-example-app, MIT) y reescribe la capa de presentación con Vite + React 18 (ver docs/05-decisiones.md D-18). El dominio, el esquema relacional y el contrato de API son los de la aplicación existente.

Las tres redes están aisladas entre sí: appnet no ve la base, monnet solo se cruza con las otras para scrapear. dbnet no tiene internal: true porque el contenedor necesita resolver el DNS de Docker y salir a Internet para apt/npm durante el build (decisión D-15).

Todas las publicaciones son en loopback: no hay un solo puerto escuchando en 0.0.0.0.

4. Flujo de una petición

sequenceDiagram

    participant P as Prisma
    participant D as PostgreSQL

    N->>F: GET /  (HTTPS por el túnel)
    F-->>N: index.html + assets
    N->>F: GET /api/articles

    D-->>P: filas
    P-->>B: objetos

Un solo origen ⇒ no hace falta CORS (el cors() del backend queda como red de seguridad para clientes externos, no como solución de arquitectura). El frontend agrega las cabeceras de seguridad y el rate limit de /api/ antes de llegar al backend.

04 — Manual de instalación

1. Objetivo

Levantar el stack completo desde cero en una máquina Windows con Docker Desktop, sin pasos implícitos. Todo lo que sigue está probado en el equipo de la práctica; los tiempos son los medidos, no estimaciones.

2. Requisitos

Componente Versión mínima Verificación
Windows 11 (probado) winver
Docker Desktop 4.30+ con WSL 2 docker version
PowerShell 5.1 (probado) o 7.x $PSVersionTable
Git cualquiera reciente git --version
Espacio en disco 40 GB libres 8,5 GB de base + imágenes + backups
RAM 8 GB (16 GB recomendado) Docker Desktop → Resources
Python 3.11+ (solo scripts auxiliares) python --version

Recursos asignados a Docker Desktop usados en las pruebas: 6 CPU, 8 GB de RAM, 60 GB de disco. Con menos de 4 GB de RAM la carga del dataset puede quedar sin memoria.

07 — Informe de optimización SQL

1. Método

  1. Se identificaron las consultas con pg_stat_statements (top por tiempo total) y se contrastaron con las operaciones reales del backend (Prisma): cada consulta de este informe corresponde a una pantalla del producto, no a un ejemplo inventado.
  2. Para cada una se capturó EXPLAIN (ANALYZE, BUFFERS) y el tiempo de ejecución con la caché caliente (segunda corrida).
  3. Se aplicó un cambio por vez, midiendo el efecto.
  4. Se probó también una optimización que no funcionó y se descartó con el número en la mano.

Scripts: db/queries/10-baseline.sql (antes) y db/queries/20-optimizado.sql (después). Evidencia cruda: evidence/05/baseline-1.txt, evidence/05/optimizado.txt, evidence/05/control.txt.

3. Análisis consulta por consulta

Q1 — count del listado (656 ms → 5,9 ms)

Plan inicial: Parallel Hash Join + Parallel Index Only Scan sobre Article_authorId_idx (2.000.000 filas × 3 workers). El join no es el problema: contar 6M de filas es O(n) y ningún índice lo evita.

Decisión: acotar el conteo a 10.000 (la interfaz solo necesita la cantidad de páginas). El plan corta al alcanzar el tope y baja a 5,9 ms.

Hallazgo mayor: la consulta que genera Prisma para este mismo caso tarda 17,8 s de promedio (5 llamadas en pg_stat_statements), contra 656 ms del SQL equivalente escrito a mano. El ORM arma una subconsulta con IN (SELECT … FROM "User" WHERE demo) que el planificador resuelve mal. Se reemplazó por SQL directo en article.service.ts (ver §5 del informe de configuración Docker).

Q2 — listado paginado (5,3 ms, sin cambios)

Usa Article_createdAt_idx y corta en 10 filas. No se tocó: no hay nada que optimizar y agregar un índice acá solo costaría escrituras.

Q2b — paginación profunda (1.933 ms → 62,6 ms)

Con OFFSET 500000 PostgreSQL lee y descarta medio millón de filas. Se reemplazó por keyset pagination: WHERE (createdAt, id) < (último de la página anterior).

Trade-off honesto: keyset no permite "saltar a la página 50" directamente; sirve para scroll infinito o "siguiente/anterior", que es el patrón real de un listado.

Q3 — filtro por etiqueta (134 ms, sin cambios)

El plan ya es bueno: Bitmap Index Scan sobre _ArticleToTag_B_idx → Index Scan sobre Article_pkey → Index Scan sobre User_pkey, 1.200 filas y 9,5 ms de ejecución. Los 134 ms incluyen planificación y JIT de la primera ejecución. Se deja como está y se documenta: es el caso que demuestra que no todo se optimiza agregando índices.

Q4 — etiquetas populares (1.033 ms → 0,69 ms)

GROUP BY sobre 6M de filas de _ArticleToTag en cada request. Se materializó el agregado:

CREATE MATERIALIZED VIEW mv_tag_counts AS
SELECT t.id, t.name, count(*) AS n
FROM "_ArticleToTag" at JOIN "Tag" t ON t.id = at."B"
GROUP BY t.id, t.name;

Trade-off: el dato puede tener atraso. El refresco se delega a n8n (§13), que es exactamente el tipo de tarea operativa que pide el enunciado.

Q5 — feed de autores seguidos (8.331 ms → 1,2 ms)

El JOIN "_UserFollows" hacía que el planificador estimara mal y terminara escaneando artículos. Reescritura:

SELECT … FROM "Article" a
WHERE a."authorId" IN (SELECT "B" FROM "_UserFollows" WHERE "A" = 42)
ORDER BY a."createdAt" DESC LIMIT 10;

Plan nuevo: Nested Loop con Index Only Scan sobre _UserFollows_AB_unique y Index Scan sobre Article_authorId_idx. 0,109 ms de ejecución.

Q6 — detalle + comentarios (7,5 ms, sin cambios)

slug es UNIQUE (índice), Comment.articleId está indexado y el subquery de conteo usa ese índice. Óptimo de entrada.

Q7 — top de artículos por favoritos (3.565 ms → 1,4 ms)

Mismo patrón que Q4: agregado sobre 6M. Vista materializada mv_article_favorites con índice único y otro por favs DESC.

Q8 — búsqueda por título (5.292 ms → 3,5 ms)

ILIKE '%texto%' no es SARGable: ningún B-tree puede resolver una subcadena con comodín inicial. Control ejecutado con enable_indexscan=off: 5.074 ms (seq scan de 6M).

Solución: pg_trgm + índice GIN. Plan nuevo: Bitmap Index Scan on Article_title_trgm_idx, 0,55 ms de ejecución.

  2. Si ya hay datos: arranca directamente (un reinicio no vuelve a clonar).

5. Failover: procedimiento manual (no automático)

# 1. detectar que la primaria no responde (monitoreo o healthcheck)
docker compose stop db

# 2. promover la réplica
./scripts/replica.ps1 promote        # pg_promote()

# 3. repuntar la aplicación
#    .env -> DATABASE_HOST=db-replica
docker compose up -d --force-recreate backend

# 4. verificar
curl http://127.0.0.1:8090/api/articles?limit=3

No hay detección automática de falla ni promoción automática. No se usa Patroni/repmgr: el enunciado advierte que la replicación por sí sola no garantiza alta disponibilidad, y afirma que si se declara failover automático hay que demostrarlo. Acá se declara failover manual, con el procedimiento ejecutado y el RTO medido.

6. Divergencia detectada (lo más importante de la prueba)

Al promover la réplica y seguir escribiendo, el nodo promovido quedó con un usuario que la primaria vieja no tiene (failover_demo). Al restaurar la topología original hubo que descartar el volumen de la réplica promovida y volver a clonar, perdiendo esa escritura.

Eso no es un defecto del procedimiento: es la naturaleza de un failover manual sin cuórum. Si la primaria "caída" en realidad solo estaba aislada (split-brain), ambas aceptarían escrituras y habría que reconciliar. Un sistema con promoción automática necesita un mecanismo de cuórum (Patroni + etcd) para evitar exactamente esto.

Consecuencia documentada: RPO ≠ 0. En replicación asíncrona se puede perder el WAL que no llegó a la réplica. En la prueba el lag era 0 bytes, así que la pérdida fue de la escritura hecha después de la promoción, no antes.

09 — Integración y despliegue continuos

1. Objetivo

Que ninguna modificación defectuosa llegue a main ni al entorno publicado, que el despliegue sea reproducible, y que si una versión nueva rompe el servicio el sistema vuelva solo a la anterior.

2. Herramienta

GitHub Actions, porque el repositorio ya vive en GitHub: no hace falta infraestructura extra ni credenciales adicionales, y los status checks se integran nativamente con la protección de rama.

3. Integración continua (.github/workflows/ci.yml)

Se dispara en push y pull_request sobre main y develop.

Job Qué hace Por qué
backend npm ci + npm run build (Nx, Node 20) el backend debe compilar antes de construir la imagen
frontend npm ci + eslint + vite build + artefacto frontend-dist lint y build son la barrera mínima de calidad
secrets gitleaks sobre todo el historial con --redact un secreto puede estar en un commit viejo, no solo en el HEAD
compose docker compose config + control de que .env no está versionado un compose inválido rompe el despliegue; un .env versionado filtra credenciales

Decisiones de diseño:

  • npm ci, no npm install: exige lockfile y garantiza que el build de CI sea el mismo que el local.
  • Node 20 fijo: el host tiene Node 26, pero CI y Docker usan la misma versión LTS.
  • permissions: contents: read: el workflow de CI no necesita escribir nada.
  • concurrency con cancel-in-progress: dos pushes seguidos no encolan dos pipelines completos.
  • gitleaks por imagen Docker: no requiere token ni licencia de la action.

6. Registro

CI publica en GHCR y el despliegue baja de ahí. Verificado: el paquete quedó público (repositorio público) y se puede bajar sin credenciales:

7. Despliegue pull-based (scripts/deploy.ps1)

No hay push desde GitHub al host: el host baja la versión que se le indica. Es el patrón correcto cuando el destino no tiene una IP pública ni un runner self-hosted.

./scripts/deploy.ps1 -Tag sha-1a2b3c4     # despliegue normal
./scripts/deploy.ps1 -Rollback            # volver a la versión anterior

Secuencia:

  1. Baja las dos imágenes antes de tocar nada. Si el pull falla, el servicio actual sigue corriendo: el despliegue aborta sin dejar el sistema a medias.
  2. Escribe el tag en BACKEND_IMAGE, FRONTEND_IMAGE y APP_VERSION.
  3. docker compose up -d --no-build --no-deps backend frontend (solo esos dos servicios).
  4. Espera salud real: GET /health a través del frontend y docker inspect en healthy.
  5. Si no queda sano en el timeout, rollback automático al tag anterior y vuelve a verificar.

El estado queda en .deploy/state.json (no versionado): current, previous, history, failed_tag si hubo rollback.

GET /health devuelve la versión desplegada:

{"status":"ok","db":"up","uptime":31.06,"version":"v1"}

Eso permite responder "¿qué está corriendo?" sin entrar al contenedor.

Acceso: http://127.0.0.1:3001/d/pi-overview. Lectura anónima habilitada solo en loopback para la demo; el usuario admin conserva su contraseña.

5.1 Prueba de anomalía (cadena completa)

Objetivo: verificar que una anomalía real recorre métrica → regla → Alertmanager → webhook, no solo que la regla existe.

./scripts/monitoreo.ps1 test-alerta -Minutos 13

El script lanza stress-ng en un contenedor efímero (16 workers, sin límite de --cpus) y sigue el estado de la regla leyéndolo de la API de reglas de Prometheus.

Momento CPU Estado de CPUAlta
t = 1 s 3,4% inactive
t = 262 s 99,9% pending
t = 564 s 99,9% firing
t = 585 s — fin de la prueba; se retira el contenedor

Alertmanager recibió la notificación 10 s después (group_wait: 10s):

{"status": "firing",

             "annotations": {"summary": "CPU del anfitrión al 100.0%",
                             "description": "CPU sostenida por encima del 85% durante 5 minutos..."}}]}

Al retirar el estrés la expresión vuelve a false, la alerta se resuelve y Alertmanager envía el resolved (send_resolved: true).

Lección registrada: la primera medición se hizo con docker run --cpus 6, que topa el contenedor en 6 de 8 vCPU (75%). La CPU se estabilizó en 77,7% y la alerta nunca disparó. Al medir capacidad con un generador de carga limitado se mide el límite del cgroup, no la del anfitrión.

6. Limitaciones encontradas (y qué se hizo)

cAdvisor no funciona en Docker Desktop

Se intentó gcr.io/cadvisor/cadvisor:v0.49.1 para métricas por contenedor. Falla al enumerar:

Failed to create existing container: /docker/<id>:
failed to identify the read-write layer ID ... 
open /rootfs/var/lib/docker/image/overlayfs/layerdb/mounts/<id>/mount-id: no such file or directory

Causa: Docker Desktop usa el snapshotter de containerd, así que /var/lib/docker/image/overlayfs no existe. Se probó también con --containerd=/run/containerd/containerd.sock --containerd-namespace=moby: el factory de containerd registra correctamente, pero no enumera los contenedores de Docker Desktop y cAdvisor cae al handler raw (series sin label name).

Decisión: se retira cAdvisor y los paneles 4 y 5 pasan a carga del sistema y red del anfitrión. El estado de cada servicio se cubre con up y con los sondeos HTTP del panel 6. Se documenta en vez de dejar un panel vacío o un contenedor privilegiado que no aporta datos.

Las métricas de "anfitrión" son las de la VM de Linux

node-exporter corre dentro de la VM de Docker Desktop, no en Windows. Mide los 8 vCPU y la memoria asignados a esa VM. Es correcto para lo que corre en contenedores, pero no es el consumo de Windows. En un servidor Linux real la distinción desaparece.

Nota de medición: la primera prueba con docker run --cpus 6 se estabilizó en 77,7% — el límite de cgroup era exactamente 6 de 8 vCPU (75%) más la carga del stack. Con --cpus 8 el contenedor seguía limitado por la cuota y la lectura no subía. La prueba correcta es sin --cpus y con sobre-suscripción (stress-ng --cpu 16): ahí la CPU llega a 100% y la regla de 85% dispara. Lección registrada: al medir con un límite de cgroup se está midiendo el límite, no la capacidad del anfitrión.

Un solo nodo de monitoreo

Prometheus, Alertmanager y Grafana corren en el mismo host que lo monitoreado. Si el host cae, no hay alerta (no hay quien la emita). La solución real es un Prometheus externo con remote_write, o un segundo nodo con Thanos/Mimir. Se declara como limitación, no se simula.

Importación de workflows

nombre=$(sed -n 's/.*"name": "\([^"]*\)".*/\1/p' "$archivo" | head -1)
n8n list:workflow | grep -F "|${nombre}" || n8n import:workflow --input="$archivo"

Primer intento fallido que vale documentar: se usaba un marcador en el volumen (/home/node/.n8n/.workflows-imported). La condición correcta es consultar la base.

Segundo error: n8n list:workflow imprime un encabezado aunque no haya workflows, así que wc -l daba 1 y el import nunca corría. Se cuentan solo las líneas con |.

3. Flujo 1 — Alerta de Prometheus a incidencia en Mantis

Nodo Qué hace

Responder 200 / Responder error devuelve el id de la incidencia o el motivo del rechazo

Autenticación del webhook

El token viaja en Authorization: Bearer <token> porque es lo que soporta http_config de Alertmanager (no manda headers arbitrarios). El flujo también acepta x-webhook-token para pruebas manuales.

El token no está en el repositorio: el JSON versionado tiene __WEBHOOK_TOKEN__ y __MANTIS_TOKEN__, y el entrypoint genera una copia en /tmp con los valores de .env antes de importar. Si el reemplazo no ocurriera, el flujo falla cerrado (autorizado exige que el placeholder ya no esté presente).

Token válido, payload correcto 200 {"ok":true,"issue":21,...} crea la incidencia

5. Limitaciones

  • El backup es lógico: 12,5 min de restauración para 8,5 GB. Un backup físico (pg_basebackup) sería mucho más rápido, pero es específico de la versión y del clúster.
  • No hay backup incremental ni envío a almacenamiento externo: si se pierde el host, se pierden backups y base. Se documenta como mejora (§15.16) y es el punto que justifica la réplica de §6.
  • El script no cifra el dump. Para datos reales habría que cifrarlo (age/gpg) antes de sacarlo del host.
  • La retención se aplica por fecha de archivo; no hay verificación de integridad del dump más allá de la restauración de prueba manual.

10. Preguntas frecuentes

¿Por qué no hay failover automático si el enunciado lo sugiere? Porque el enunciado pide replicación, y el failover automático con Patroni requiere consenso de 3 nodos. Se implementó lo que se puede demostrar en un host: promoción manual medida en 8,6 s y procedimiento escrito. Se declara como limitación en vez de simularlo.

¿El sistema aguanta un usuario real? Aguanta el tráfico de la práctica (prueba de carga con 100 usuarios concurrentes). No está dimensionado para producción: un backend, un frontend y un solo host.

¿Qué pasa si se cae Cloudflare? La aplicación sigue funcionando en la LAN (http://192.168.1.8:8090 no está publicado; el acceso es por 127.0.0.1 en el host). Se pierde el acceso remoto, no el servicio.
